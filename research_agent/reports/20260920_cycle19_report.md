## 仮説: `h-soft-anchor-disfluency-gate`(完了、結果は部分的)

**背景**: サイクル18の`h-soft-anchor-generalization-guest-talk`は、
`soft_anchor_replay`(前回の翻訳結果を助言的に添えて継続バッチを翻訳
させる仕組み)のクロスバッチNE改善効果が別クリップでも再現することを
確認した一方、原文が言い淀み・断片的な場合に「アンカーに合わせて内容を
捏造する」という新しい失敗モードを発見しました(スパン69: 原文
`"our paper, we just like a like like a AIM to"`に対し、アンカーありの
訳が架空の固有名詞「AIME」を捏造)。本仮説はその具体的な改善案として、
**新規差分テキストの単語数が閾値未満(`GATE_MIN_WORDS=5`)のバッチでは
アンカーを無効化し、ゼロからの再翻訳にフォールバックする**「ゲート」を
実装・検証するものです。

**実装**: `prefix_lock_replay.py`の`_extract_spans()`/`_translate_once()`
をそのまま再利用し、`gated_soft_anchor`条件を新たに実装した
`soft_anchor_disfluency_gate_replay.py`を作成。過去2つの仮説で使った
両方の録音済み実験JSON(元クリップ15スパン、ゲストトーク83スパン)に
対し、`baseline_replay`/`soft_anchor_replay`/`gated_soft_anchor`の3条件×
各2回リピートを実行しました(翻訳呼び出し1458回+忠実度審査呼び出し
最大294回)。

**交絡チェック**: 両ソース実験JSONの`models`ブロック
(`llm_model=gemini-3-flash-preview`, `gemini_thinking_budget=0`)は完全に
一致しており、config差分による交絡はありません。なお実装上、
`LLMTranslator`インスタンスは最初のソースファイルの`models`設定で1回だけ
作成し、2つ目のソースにもそのまま使い回す作りになっている点に気づきました
(今回はたまたま両ソースのmodelsが一致していたため無害でしたが、将来
modelsが異なるソースを組み合わせるリプレイ仮説ではソースごとに
`LLMTranslator`を作り直す必要があります。忘れずに次のセッションへ
申し送りします)。

**結果**:

| クリップ | ゲート発動率(i>0バッチ中) | 条件 | 平均クロスバッチNE | 平均忠実度スコア |
|---|---|---|---|---|
| 元クリップ(15スパン) | 8/20 (40%) | baseline_replay | 0.613 | 98.67 |
| | | soft_anchor_replay | 0.233 | 98.33 |
| | | gated_soft_anchor | 0.408 | 96.67 |
| ゲストトーク(83スパン) | 71/125 (**57%**) | baseline_replay | 0.622 | 92.71 |
| | | soft_anchor_replay | 0.123 | 88.41 |
| | | gated_soft_anchor | 0.547 | 90.67 |

- **NEは予測通り、両クリップともbaselineとsoft_anchorの間に収まりました。**
  ただし`GATE_MIN_WORDS=5`の発動率が予測より大幅に高く(特にゲストトーク
  クリップで対象バッチの57%がゲートされ、「大半のバッチは短くないので
  効果の大半は残るはず」という予測の前提が外れました)、その結果
  ゲストトーククリップではNE改善のうち相対的にわずか約12%しか
  維持できず(0.622→0.547)、soft_anchorが達成した約80%改善
  (0.622→0.123)の大半を犠牲にする形になりました。
- **標的にした具体的な失敗ケース(スパン69)はゲートによって修正されまし
  た。** 忠実度スコアはsoft_anchor条件の50点からgated条件で100点
  (baselineと同じ)に回復し、捏造が起きなくなったことを確認しました。
- **一方で集計上の平均忠実度は、ゲートが機能した証拠として頼れないことが
  分かりました。** 元クリップでは`gated_soft_anchor`(96.67)が
  `baseline_replay`(98.67)にも`soft_anchor_replay`(98.33)にも劣る、
  予測外の順序になっています。原因を調べたところ、忠実度審査
  (`judge()`)は各条件・各スパンにつき1回(`repeats[0]`のみ)しか
  呼んでおらず、ゲートが一切発動しなかったスパン(コード上
  `gated_soft_anchor`は`soft_anchor_replay`と完全に同一の処理になる
  はず)だけを取り出して両条件のスコア差を見たところ、元クリップで
  -30〜+5点(n=7)、ゲストトーククリップで-5〜+45点(n=13)という、
  単なるLLMサンプリングのばらつきだけでこれだけの差が出ることが
  分かりました。これはゲートが実際に発動したスパンでの平均差
  (元クリップ0.00点 n=8、ゲストトーク+1.84点 n=68)と同程度かそれ
  以上の幅であり、**現在の「条件ごとに1回だけ審査する」設計では、
  集計上の忠実度差がゲートの効果なのかサンプリングノイズなのか
  区別できません。**

**結論**: `status`は`tested`としました(`abandoned`にはしていません)。
ゲートの仕組み自体は標的にした具体的な失敗パターン(スパン69の捏造)には
有効に機能することを確認できましたが、(1)`GATE_MIN_WORDS=5`は
言い淀みの多い素材に対しては閾値が高すぎ、NE改善効果の大半を犠牲に
してしまうこと、(2)現状の実験設計(条件ごとに忠実度審査1回のみ)では
集計レベルでの正味の改善をノイズと区別して主張できないこと、の2点が
分かりました。次の一手としては、(a)閾値を2〜3語程度に下げて再検証する、
(b)`judge()`を各リピートで呼んでスパンごとのノイズ幅を実際に測定できる
ようにする、の2点を推奨します。

なお本実験もリプレイ/分析系のスクリプトであるため、`experiments/
results.csv`への行追加は行っていません(サイクル17・18と同じ既存の
前例に従っています)。
