## 仮説: `h-soft-anchor-gate-recalibrated-noisefloor`(完了、結果は部分的、設計ミスあり)

**背景**: サイクル19の`h-soft-anchor-disfluency-gate`は、単語数ゲート
(新規差分テキストが`GATE_MIN_WORDS`未満の場合はアンカーを無効化して
ゼロから再翻訳)を実装しましたが、(1)閾値`GATE_MIN_WORDS=5`が実際の
単語数分布を確認せずに決められたため発動率が予測よりはるかに高く
(元クリップ40%・ゲストトーク57%)、NE改善効果の大半を犠牲にしてしまい、
(2)忠実度審査(`judge()`)が各条件・各スパンにつき1回(`repeats[0]`のみ)
しか呼ばれておらず、ノイズの実測ができていない、という2つの較正課題を
残していました。本仮説はその両方を修正するフォローアップです。

**設計時の事前作業**: 実験を組む前に、既存の2つの録音済みソース実験の
`delta_text`単語数ヒストグラムを実際に計算しました(i>0の対象バッチ
145件)。中央値は両クリップとも4〜5語であることが分かり、
`GATE_MIN_WORDS=5`は中央値以上を丸ごとゲートしていたことになります。
`GATE_MIN_WORDS=2`に下げると、発動率は元クリップ10%(2/20)、
ゲストトーク16%(20/125)まで下がると試算し、これを採用しました。

**実装**: `soft_anchor_disfluency_gate_replay.py`の`_run_gated_condition()`
をそのまま再利用し、モジュールレベルの`GATE_MIN_WORDS`のみ2に変更した
`soft_anchor_gate_recalibrated_replay.py`を新規作成。加えて、忠実度審査
`judge()`を各条件の`repeats[0]`だけでなく**全リピートで**呼ぶように変更し、
スパンごとのスコアのばらつき(標準偏差)を直接測定できるようにしました。
両ソース実験JSON(元クリップ15スパン、ゲストトーク83スパン)に対し、
3条件×各2回リピートを実行(翻訳呼び出し1458回、バッチ・スパン構成は
サイクル19と同一のため件数も同一。忠実度審査呼び出しは前回の最大294回
から倍増して588回)。

**交絡チェック**: 両ソース実験JSONの`models`ブロック
(`llm_model=gemini-3-flash-preview`, `gemini_thinking_budget=0`)は完全に
一致しており、config差分による交絡はありません。

**結果**:

| クリップ | ゲート発動率(i>0バッチ中) | 条件 | 平均クロスバッチNE | 平均忠実度スコア |
|---|---|---|---|---|
| 元クリップ(15スパン) | 2/20 (10%) | baseline_replay | 0.665 | 99.0 |
| | | soft_anchor_replay | 0.232 | 99.2 |
| | | gated_soft_anchor | 0.290 | 98.2 |
| ゲストトーク(83スパン) | 20/125 (16%) | baseline_replay | 0.649 | 91.8 |
| | | soft_anchor_replay | 0.123 | 89.4 |
| | | gated_soft_anchor | 0.307 | 90.0 |

- **NEはヒストグラムに基づく予測通り、大幅に改善しました。** 発動率が
  サイクル19の40%/57%から10%/16%まで下がった結果、ゲストトーククリップ
  の`gated_soft_anchor`のNEは0.547(サイクル19)から0.307(今回)まで
  改善し、soft_anchor単体(0.123)にかなり近づきました。閾値の較正が
  意図通りに効いたことを確認しました。
- **忠実度の正味の改善は、今回きちんと測ったノイズ幅と比べても依然として
  確認できませんでした。** 今回は`judge()`を全リピートで呼び、ゲートが
  一切発動しなかったスパン(コード上、条件間で処理が完全に同一になる
  はずの箇所)でのスコアのばらつきを直接測定しました。結果、標準偏差は
  元クリップで3.23点(n=52、サイクル19の事後推定「-30〜+5点」より
  精密に測定)、ゲストトークでは**17.72点**(n=251)と、サイクル19の
  事後チェックが示唆した幅と同等かそれ以上の非常に大きなノイズである
  ことが分かりました。一方、実際にゲートが発動したスパンでの
  `gated_soft_anchor`と`soft_anchor_replay`の平均忠実度差は、元クリップ
  0.0点(発動2スパン)、ゲストトーク4.0点(発動20スパン、個々の差は
  -5〜+50点とばらつきが大きい)にとどまり、いずれもノイズ幅の内側に
  埋もれています。**閾値を較正してもなお、ゲートによる正味の忠実度改善は
  統計的に主張できません。**
- **設計ミスを発見しました(分析中、計画段階では見落とされていました)。**
  本仮説の説明文には「`GATE_MIN_WORDS=2`でも標的の失敗ケース(ゲストトーク
  スパン69、バッチ1、差分テキスト`"AIM to"`、2語)は引き続きゲートされる」
  と明記していましたが、実際のゲート条件は
  `len(delta_text.split()) < GATE_MIN_WORDS`という**厳密な未満**判定です。
  そのため`GATE_MIN_WORDS=2`のとき、ちょうど2語の差分は
  `2 < 2`が偽となりゲートされません。今回の実行結果JSONで確認したところ、
  スパン69の`gated_batch_indices`は空配列`[]`で、この仮説シリーズが
  一貫して標的にしてきた「AIME」捏造ケースは、今回**一度もゲート機構を
  通っていませんでした**。それでもスパン69の`gated_soft_anchor`条件の
  忠実度スコアは今回たまたま100点(捏造なし)でしたが、これはゲートの
  効果ではなく、アンカーあり翻訳のLLMサンプリングのばらつきによる
  偶然の結果である可能性が高いです。計画段階で比較演算子(`<`)を
  実データの境界値(ちょうど2語のケース)に対して検証していなかったこと
  が原因です。

**結論**: `status`は`tested`としました(`abandoned`にはしていません)。
NEの改善は閾値較正の狙い通りに実現しましたが、忠実度面の正味の改善は
今回初めて正しく測定したノイズ幅と比べても確認できず、加えて標的だった
具体的な失敗ケース(スパン69)が実は今回のゲート条件で一度も発動して
いなかったという設計上の見落としが判明しました。このゲート方式の
一般的なアイデア自体を否定するものではありませんが、次に試すなら
`GATE_MIN_WORDS=3`(`<=`ではなく`<`のままでも2語ケースを含められる)
を推奨します。また、`judge()`を1回だけ呼ぶ設計はこのコードベースの
どこでも(このゲート仮説に限らず)信頼できないことが今回の実測
(ゲストトークで標準偏差17.7点)で裏付けられたため、忠実度に基づく
今後の仮説すべてに対して同様のノイズ幅チェックを標準手順とすることを
推奨します。

なお本実験もリプレイ/分析系のスクリプトであるため、`experiments/
results.csv`への行追加は行っていません(サイクル17〜19と同じ既存の
前例に従っています)。
