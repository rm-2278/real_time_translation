# サイクル100 結果レポート (2026-11-24)

## 概要: 節目のサイクル100 — 実行環境でAPIキーが初めて設定された状態を確認し、92サイクルぶり以上に新規のライブAPI実験を1件実行、鮮明な「ネガティブ」結果を得た

本サイクルはスケジュール実行(cron)によるもので、`current_state: SEARCH_PAPERS`
(前セッション=サイクル99の `REFLECT` が新サイクル開始として進めた状態)から
再開しました。本セッションでは
`SEARCH_PAPERS -> EXTRACT_PAPERS -> READ_PAPERS -> GENERATE_HYPOTHESES -> HUMAN_APPROVAL -> RUN_EXPERIMENTS -> ANALYZE_RESULTS -> WRITE_REPORT`
まで全ステートを進めています。

**最大のニュース**: 本サイクルの `RUN_EXPERIMENTS` 環境チェックで、
`DEEPGRAM_API_KEY` / `GOOGLE_API_KEY` / `OPENAI_API_KEY` が**この自律パイプラインの
履歴上初めて**、このセッションのシェル環境に実際に設定されていることを確認しました
(過去のPLAYBOOK.mdの記述はすべて「未設定の場合がある」という前提でした)。
Deepgram REST (`/v1/projects`) とGemini REST (`/v1beta/models`) はいずれも200で到達可能
でしたが、**Deepgram のライブ音声文字起こし用WebSocket(`listen`)のアップグレード
ハンドシェイクは、サイクル5以来まったく同じ `HTTP 400 "Connection header did not
include 'upgrade'"` で依然ブロックされており**、`api.openai.com` も依然CONNECTレベル
で403拒否されたままでした。つまり「鍵が設定されたこと」自体は新しい事実ですが、
実際に新しいライブ音声を取り込む実験や、OpenAIを使う実験ができるようになったわけ
ではありません。一方で、**既存の録音済みテキストをGeminiだけでリプレイする実験は
元々ブロックされていなかった**ため、本サイクルではそのような新規仮説を1件、
実際にライブAPI呼び出し付きで実行できました。

## SEARCH_PAPERS / EXTRACT_PAPERS / READ_PAPERS: 新規文献3件を追加

サイクル99同様、まず複数の観点でWebSearchを実施しました: ストリーミング翻訳の
安定化ポリシー、字幕のフリッカー低減、カスケード対エンドツーエンドのレイテンシ
比較 — これらはすべて既存の`papers.json`(106件→読了103件)に既に登録済みの
候補しか見つからず、既存文献ベースの網羅性の高さを改めて裏付けました。

続いて、より新しい2つの観点(LLM-as-judge評価の信頼性、EN<->JA翻訳評価)で
検索したところ、以下3件の未登録文献が見つかりました(すべて`arxiv.org`/
`aclanthology.org`へのWebFetchは今回もENOTFOUND — 従来通りWebSearch要旨による
代替取得):

- **`rate2026-beyond-literal-mapping-nontransliteval`**(ACL 2026, arXiv:2601.07338,
  "Beyond Literal Mapping"): 慣用句・比喩など非直訳的翻訳の人手評価データセット
  MENT(7,530件)と、マルチエージェント型judge「RATE」を提案。コア知見:
  単純なLLM-as-judgeは従来指標より優れるが、(1)知識カットオフの古さ、(2)採点の
  不安定さという2つの具体的な欠陥があり、それぞれをSearchエージェント(外部知識
  検索)とComparisonエージェント(他候補とのペア比較によるキャリブレーション)
  で補う設計。
- **`jptlbench2026-anchored-pairwise-ja-en`**(arXiv:2601.00223, Shisa.AI):
  EN<->JA双方向70項目のベンチマーク。絶対スコアではなく、固定・バージョン管理
  された20件のアンカー出力との**ペア比較**を行い(1評価あたり約1400回の比較)、
  Bradley-Terryモデルで勝率と0-10の正規化スコアに集約する手法。BLEU/COMETは
  高品質帯で判別力を失うと指摘。
- **`wat2026-patent-claims-task2-findings`**(WAT 2026, Anthology 2026.wat-1.11):
  特許クレームのEN<->JA翻訳評価の共有タスク第2回。前回の知見として「この領域では
  参照なし自動指標が人間評価とあまり相関しない」ことが確認されている — 本リポジトリ
  自身もreference-freeなLLM judgeに依存しているため、留意すべき点として記録。

本リポジトリの既存judge-noise系統(推論順序、ブロック順序、holistic対decomposed、
repeat数、冗長性バイアスなど、`experiments/results.csv`の2026-10-19〜10-27の各行)
を`git log`とキーワードgrepで確認しましたが、いずれも「単独の絶対スコア評価」の
バリエーションであり、**ペア比較形式そのものを試した仮説は一度もない**ことを
確認しました — 重複ではなく、本当に未検証の角度です。

## GENERATE_HYPOTHESES: 新仮説1件を追加

上記2件(RATE/MENTのComparisonエージェント、JP-TL-Benchのアンカー付きペア比較
+Bradley-Terry)に根拠づけた新仮説 **`h-judge-pairwise-anchored-comparison-
sensitivity`** を追加しました: 「ペア比較形式のjudgeは、本リポジトリ既知の
小さな(10点差)実在する忠実度差分を、独立した2回の絶対スコア呼び出しより
一貫して検出できるか?」というもので、推定コスト$0.01・既存Gemini呼び出しのみ
(新規Deepgram不要)と判定し、バックログ上限(~6件)の範囲内(当時4 queued +
1 proposed)に収まるため追加しました。

## HUMAN_APPROVAL: 新仮説を自動承認

`check-budget 0.01` が `AUTO_APPROVE` を返し、`uses_existing_clips=true` だったため、
通常の自動承認パス(`approval: auto_approved`, `status: queued`)を適用しました。
これは「エスカレーション済み(`needs_human`)の仮説を自分で承認し直す」自己承認
ブロック(サイクル36で確認済みの安全ゲート)とは異なる、通常の新規承認フローであり、
書き込みは問題なく成立しました。既存の1件(`h-judge-repeat-independent-batches-
corrected-design`, `needs_human`)は今回も変更せず、人間の合図待ちのまま保持しています。

## RUN_EXPERIMENTS: 新規仮説を実際に実行、環境チェックで鍵設定を確認

環境チェックの結果(上記の通り): 3つのAPIキーがすべて設定済み、ffmpegも利用可能、
Deepgram/Gemini REST到達可能、だがDeepgramのライブWebSocketとOpenAIは依然ブロック。
`python3.13`でのvenv構築(PLAYBOOK.md記載の回避策)を実施し、`websockets`ライブラリ
での実機WebSocket確認スクリプトも実行して再確認しました。

キュー済み5件(新仮説含む)のうち、新仮説**のみ**が「既存の録音済みテキストに
対するGeminiのみの新規judge呼び出し」で完結する設計だったため、唯一実行可能
でした。新規スクリプト`judge_pairwise_comparison.py`を実装し(ruffチェック通過)、
`experiments/20260916_compression_actions_prompt.json`のbaseline_replay
(retention_score=75)とcompression_actions(retention_score=85)という既知の
10点差ペアに対し、A/Bスロットを入れ替えながら20回のペア比較judge呼び出しを実行
しました。他の4件(OpenAI必須、Deepgram WS必須×2、人間の視聴時間待ち)は本サイクル
も再確認の上ブロックのままでした。

## ANALYZE_RESULTS: 鮮明な「ネガティブ」結果 — 位置バイアスが完全にコンテンツ信号を覆い隠した

結果は非常に明確でした: **20回すべてでjudgeは「スロットB」を選択**
(`verdict_slot_a_rate=0.0`)。これはcompression_actions(本来「良い」方)が
スロットAにあるときの勝率が0.0、スロットBにあるときの勝率が1.0という、完全に
位置と一致した結果で、内容を正しく評価した痕跡が全くありません。各回答には
「tokenizer」対「token errors」のような具体的な内容への言及があり、単なる
定型文の繰り返しではなく、位置バイアスを後付けで正当化するような推論テキストが
生成されていました(プロンプト構築・スロット割当ロジックは生データと突き合わせて
再確認済みで、コードの不具合ではないと判断)。

**結論**: `jptlbench2026`/`rate2026`が示唆する「ペア比較の方がjudgeを安定化
できる」という前提は、少なくとも今回の素朴な2スロット・ペア比較プロンプト設計
では**完全に裏目**に出ました。既存の単独絶対スコア方式(`judge()`)より明確に
劣る結果であり、このままでは採用できません(単一ペアでの検証であり、他の
プロンプト表現やスキーマでは結果が変わる可能性はありますが、このサイクルで
試した具体的な設計は不採用と判断しました)。`hypotheses.json`の
`h-judge-pairwise-anchored-comparison-sensitivity`は`status: tested`、
`experiments/judge_pairwise_comparison.json`に全22行の詳細を記録しています。
Deepgram新規支出ゼロ、$0.01をログ済みです。

  視聴・評価時間待ちです(環境側の問題ではありません)。
